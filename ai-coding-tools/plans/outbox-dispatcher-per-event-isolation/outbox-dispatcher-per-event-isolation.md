# Outbox Dispatcher Per-Event Isolation

## Context

[Known Bug 2](../../../docs/KNOWN_ISSUES.md) (basket module): `BasketOutboxDispatcher.dispatch()` publishes an event and only then calls `markAsProcessed`. `InMemoryMessageBus.publish` calls `ApplicationEventPublisher.publishEvent` synchronously, so a listener exception propagates straight out of `dispatch()` — the poisoned event is never marked processed (so it retries every 5s forever) and, because the loop stops there, every later event in that batch is silently skipped too. There is no dead-letter path and no retry limit; the HTTP caller that triggered the original write sees a 202 and never learns anything failed.

Investigated whether this shape exists elsewhere before scoping the fix: [CatalogOutboxDispatcher.java](../../../SpringBoot-EshopModularMonolith/modules/catalog/catalog-core/src/main/java/com/github/eshopmodularmonolith/catalog/products/infrastructure/messaging/CatalogOutboxDispatcher.java) has the identical loop shape (publish-then-markAsProcessed, no try/catch) — same defect. Ordering has no outbox dispatcher at all yet (`Order` never calls `addDomainEvent`, tracked separately as [Backlog item 5](../../../docs/BACKLOG.md), deliberately deferred pending a real consumer), so it isn't affected today — but it's a third instance of this exact shape waiting to happen the moment that trigger fires.

Known Bug 2's own Action Required frames two things: isolating each event so one failure doesn't stop the batch, and separately deciding long-term retry semantics (attempt counter + dead-letter state) for the poisoned event itself. Confirmed with the user: this plan does **isolation only** — the poisoned event still retries every 5 seconds indefinitely after this fix, it just no longer takes its neighbors down with it. Attempt-counting/dead-lettering would additionally touch the `OutboxEventStore` port and both persistence adapters — out of scope here, left as the narrowed remainder of Known Bug 2.

Raised during planning: since the fetch-loop-isolate-mark shape is identical in both existing dispatchers and would otherwise need to be hand-copied into every future one, this plan extracts it into a shared collaborator rather than duplicating the fix twice. Considered an abstract base class (template method) first; chose composition instead, since it's the idiom the rest of this codebase already uses for behavior sharing (`OutboxEventStore`, `MessageBus`, repositories are all interfaces injected into plain classes — no existing behavior-sharing class hierarchy) and it keeps `MessageBus` a direct, visible field of each dispatcher instead of something reached through a protected base-class accessor.

Also raised during planning: since `OutboxEventProcessor` is a genuinely shared, standalone collaborator (used by both dispatchers today, and by any future one), it should be built and proven directly with its own test in the `shared` module — not proven only indirectly through `BasketOutboxDispatcherTest` and then re-proven a second time through catalog's. This reorders the work: the isolation loop is designed, TDD'd and owned by `OutboxEventProcessorTest` first; each dispatcher's own test then only needs to prove it's wired correctly, not re-prove the loop.

## Design decisions

- **New `OutboxEventProcessor` in `shared.infrastructure`** (same package as `MessageBus`, `OutboxEventStore`, `OutboxEventSubscriber`) — a plain, non-abstract class. It owns `OutboxEventStore` and implements the fetch-loop-isolate-mark logic once as `public void dispatchPendingEvents(EventPublisher publish)` — fetch, then per event: `try { publish.publish(event); outboxEventStore.markAsProcessed(event); } catch (Exception ex) { log and move on }`. Built and tested directly in the shared module — it depends on nothing module-specific, so it needs no dispatcher to exist in order to be exercised.
- **New `OutboxEventPublisher` functional interface** in `shared.infrastructure`: `void publish(DomainEvent event)`. This is the seam each module plugs its own "which event maps to what outgoing message" logic into, passed as a method reference.
- **`BasketOutboxDispatcher` and `CatalogOutboxDispatcher` hold an `OutboxEventProcessor` field** (constructed from their own `@Qualifier`-ed `OutboxEventStore`) alongside their existing `MessageBus` field — no inheritance, no change to Spring wiring or bean qualifiers. Each keeps its own `@Scheduled(fixedDelay = 5000) public void dispatch() { outboxEventProcessor.dispatchPendingEvents(this::publish); }` (same cadence as today); `publish(DomainEvent event)` becomes a private method holding exactly the `instanceof` check + mapping + `messageBus.publish(...)` call each already has today. No change to the public `dispatch()` contract either dispatcher's tests currently exercise.
- **Logging convention:** `private static final Logger logger = LoggerFactory.getLogger(OutboxEventProcessor.class)` via `org.slf4j`, matching the existing pattern in [BasketCheckedOutHandler.java](../../../SpringBoot-EshopModularMonolith/modules/basket/basket-core/src/main/java/com/github/eshopmodularmonolith/basket/basket/application/features/checkoutbasket/BasketCheckedOutHandler.java). Log at `error` with the event's `eventId()` and `eventType()` — both available on every `DomainEvent`, so `OutboxEventProcessor` needs no per-event-type-specific fields.
- **Not adding retry/attempt-count/dead-letter state** — that's the explicitly deferred half of Known Bug 2, requiring an `OutboxEventStore` port change; recorded back into the doc, not silently dropped.
- **Fakes replace Mockito mocks throughout this change.** `OutboxEventProcessorTest` (shared module) gets its own `FakeOutboxEventStore` — a third copy of the same tiny in-memory implementation basket-core and catalog-core already each have, matching that established one-fake-per-module pattern — and needs no `MessageBus` fake at all: `OutboxEventPublisher` is exercised directly as a bare lambda that throws for one event and records the other. `BasketOutboxDispatcherTest` and `CatalogOutboxDispatcherTest` each get a `FakeMessageBus` (implements `MessageBus`, records published messages, no failure-injection needed — see below) replacing their current `mock(MessageBus.class)`/`verify(...)`. Per [TESTING_CONVENTIONS.md](../../../docs/TESTING_CONVENTIONS.md), faking at the port and asserting outcomes is preferred over mocking and verifying a collaborator was called.
- **Dispatcher-level tests only prove wiring, not the isolation loop again.** Since `OutboxEventProcessorTest` proves the try/catch/retry behavior directly, `BasketOutboxDispatcherTest` and `CatalogOutboxDispatcherTest` don't need their own poisoned-event scenario — each just needs its existing happy-path test (a recognized event gets translated and published) converted onto `FakeMessageBus`, confirming the dispatcher composes the processor and its own `publish(...)` mapping correctly. This avoids proving the same loop logic three times.

## Testing rigor

- **`OutboxEventProcessor`'s isolation loop**: strict TDD red → green, directly in the shared module — new deterministic control-flow logic with real regression risk, and now the natural, standalone place to prove it.
- **Wiring `BasketOutboxDispatcher` and `CatalogOutboxDispatcher` to `OutboxEventProcessor`**: tests-alongside-implementation for both — this is applying an already-proven, already-tested collaborator via a mechanical composition change (add a field, delegate, move the mapping into a private method), not new logic. Each dispatcher's existing happy-path test is converted onto `FakeMessageBus` alongside the change.
